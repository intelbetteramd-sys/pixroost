# Источники: что можно подключить

Главное обещание Pixroost — «все диски в одном месте». Но у каждого сервиса свои правила доступа.
Здесь зафиксировано, что реально возможно, и как мы обходим ограничения **законно** — без
парсинга сайтов, неофициальных API и хранения паролей пользователей.

> Пометка **⚠️ проверить в прототипе** — документация сервиса факт не подтверждает, и он проверяется в спайке или
> прототипе на шаге, где появляется этот код.

## Подробно

### Галерея телефона (включая iCloud Фото)

- **iOS:** PhotoKit (`PHPhotoLibrary`, `PHAsset`, `PHAssetResourceManager`). Если на iPhone включены
  «Фото iCloud», через PhotoKit доступна **вся iCloud-медиатека**: оригиналы подгружаются из iCloud по запросу
  (`isNetworkAccessAllowed`). Это единственный законный способ читать iCloud Фото — публичного серверного API нет.
- **Android:** MediaStore. Видно только то, что лежит на устройстве. Облачные копии Google Фото, которых нет
  на устройстве, недоступны. Как читаем (по [спайку S-02](https://github.com/intelbetteramd-sys/pixroost/issues/22)):
  - **индекс** — полный проход по MediaStore: на 11 000 фото это 0,1–0,3 с даже на недорогом телефоне.
    Метаданные сохраняются в нашей БД, лента листается из неё. Постраничное чтение MediaStore не нужно;
  - **изменения** — на Android 11+ по `GENERATION_MODIFIED` больше сохранённого поколения; если сменилась
    `MediaStore.getVersion`, пересчитываем всё. Удалённые находим сравнением списков ID. На Android 8–10 —
    по дате изменения и сравнению ID;
  - **превью** — системные, через `ContentResolver.loadThumbnail` (Android 10+). Декодировать оригиналы для
    сетки нельзя: на Redmi Note 9 это около 4,5 кадра в секунду против плавных 60.
- **Разрешения:** полный доступ или ограниченный (iOS Limited Library, Android 14+ «выбранные фото»).
  С ограниченным доступом работаем, но показываем, что видим не всё.
- **Google Play:** доступ ко всем фото (`READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO`) разрешён приложениям,
  для которых это основная функция (галерея, бэкап) — нужно задекларировать в Play Console.
- **Удаление:** только через системный диалог подтверждения. Фото попадают в «Недавно удалённые»
  (iOS, 30 дней) / корзину (Android 11+). На Android 8–10 корзины у галереи нет, поэтому в v1.0 Pixroost
  из галереи там не удаляет и объясняет почему ([ADR 0011](../architecture/adr/0011-cleanup-safety-rule.md)).
  **Внимание:** при включённых iCloud Фото удаление на iPhone удаляет
  фото и из iCloud — интерфейс обязан об этом предупредить.
- **Корзина на Android:** хранит файлы 30 дней (`DEFAULT_DURATION_TRASHED` в AOSP), точный срок отдаёт
  `DATE_EXPIRES` в MediaStore. Во многих галереях производителей корзина MediaStore не видна, поэтому вернуть
  файл предлагает сам Pixroost: «Восстановить» в журнале уборки (`createTrashRequest(uris, false)`, системный
  диалог).
- Samsung Gallery синхронизируется с OneDrive, удаление и правки идут в обе стороны
  (по данным [Samsung Support](https://www.samsung.com/latin_en/support/apps-services/can-i-sync-gallery-photos-with-onedrive/)).
  Папку в OneDrive пользователи называют «Samsung Gallery», но официально её имя не описано (⚠️ проверить
  в прототипе на телефоне Samsung). Поэтому до проверки на телефоне Samsung весь подключённый личный OneDrive
  и галерея для правила безопасности — одно хранилище
  ([домен хранения](../architecture/data-model.md#домен-хранения)), а имя папки — только дополнительный признак.

### Яндекс Диск

- Официальный [REST API](https://yandex.ru/dev/disk/rest) с входом через Яндекс ID (OAuth).
- Плоский список всех файлов с фильтром по типу медиа, превью, квота (`total_space` / `used_space`),
  MD5 и SHA-256 в метаданных — отлично для точных дублей без скачивания.
- Удаление — в корзину Диска, она хранит файлы 30 дней. Возврат — с `overwrite=false`, то есть без перезаписи
  файла, который появился по тому же пути.
- Регистрация приложения: [oauth.yandex.ru](https://oauth.yandex.ru/) (бесплатно), тип «для авторизации
  пользователей». У типа «для доступа к API или отладки» нет платформ: адрес возврата у него зафиксирован
  на странице с кодом, который пользователь копирует вручную. Тип после создания не меняется.
- С 3 июня 2026 приложение Яндекс Диска для ПК работает только по подписке Яндекс 360
  ([Skillbox Media](https://skillbox.ru/media/code/yandeks-otklyuchit-oblachnye-funkcii-yandeks-diska-na-pk-dlya-polzovateley-bez-podpiski/)).
  Бесплатные пользователи не могут синхронизировать Диск с папкой на ПК, поэтому подключение через API —
  основной путь и на телефоне, и на ПК.
- **Вход** (по [спайку S-05](https://github.com/intelbetteramd-sys/pixroost/issues/25)) — PKCE без секрета
  приложения:
  - Android: адрес возврата `yx<client ID>:///auth/finish?platform=android`; Яндекс создаёт его сам для платформы
    «Android-приложение» (пакет и SHA-256 подписи);
  - ПК: `http://127.0.0.1:<порт>/callback` на платформе «Веб-сервисы». Произвольный порт не описан, поэтому порт
    фиксированный и регистрируется заранее.
- **Токен** живёт год. Обновить его без секрета приложения нельзя (`invalid_client: Wrong client secret`), а секрет
  в приложении не храним: через год пользователь входит заново.
- Хэши MD5 и SHA-256 приходят в списке файлов (`/v1/disk/resources/files`) без скачивания. Признак общей папки
  (`share`) этот список не отдаёт: для владельца файлов из общей папки он без `share`, для участника их там нет
  вовсе, поэтому общие папки ищет обход дерева. В ответах ресурса бывает недокументированный ключ `sizes`
  (превью), коннектор его игнорирует.
- Без подтверждения аккаунта разработчика через Госуслуги на странице входа, по документации Яндекса, может
  появляться предупреждение; при тестовом входе в 2026-10 его не было.

### Dropbox

- API v2, OAuth 2 с PKCE — подходит для публичных клиентов без секрета. По спайку S-05:
  - вход и обновление токена работают без секрета; токен живёт 4 часа, refresh token выдаётся с параметром
    `token_access_type=offline`;
  - в App Console нужно разрешить публичных клиентов («Allow public clients»);
  - адрес возврата сверяется целиком, вместе с портом: на ПК порт фиксированный (`http://127.0.0.1:<порт>/callback`),
    на Android — своя схема приложения;
  - `content_hash` приходит у каждого файла.
- Инкрементальная синхронизация через `list_folder` + курсор, превью, квота (`get_space_usage`).
- Удалённые файлы хранятся 30, 180 или 365 дней в зависимости от тарифа. API срок не отдаёт, поэтому в журнале
  уборки записывается 30 дней. Возврат — `files/restore` по `rev` из ответа `delete_v2`; поведение при занятом
  пути не документировано, поэтому путь проверяется прямо перед возвратом.
- Хэш `content_hash` — SHA-256 по блокам 4 МБ; для сравнения с локальными файлами считаем так же.
- Приложение в режиме разработки: до 500 пользователей, после 50-го есть две недели, чтобы подать заявку
  на production.

### OneDrive

- Microsoft Graph, OAuth 2 с PKCE, личные аккаунты Microsoft.
- Инкрементальная синхронизация через `delta`, превью, квота диска, удаление в корзину.
- Корзина хранит файлы 30 дней, но если она заполнена, OneDrive удаляет старые файлы через 3 дня. Поэтому
  в журнале уборки для OneDrive записывается срок 3 дня. Вернуть из корзины через API
  (`POST /me/drive/items/{id}/restore`) можно только в личном OneDrive.
- Вход для личных аккаунтов — через `login.microsoftonline.com/consumers`, без секрета (платформа «Мобильные
  и классические приложения», «Разрешить потоки общедоступных клиентов»). На ПК адрес возврата
  `http://localhost/callback`: порт Microsoft не сверяет.
- Хэши: гарантирован только `quickXorHash`; `sha1Hash` для личных аккаунтов Microsoft объявил устаревшим
  с июля 2023 без гарантий наличия. Ни `quickXorHash`, ни `sha1Hash` удаление не разрешают (нужен SHA-256
  от скачанного файла).
- Регистрация приложения в Microsoft Entra бесплатна, но нужен свой каталог (тенант): личный аккаунт Microsoft
  без каталога регистрировать приложения не может. Каталог создаётся вместе с аккаунтом Azure, который требует
  проверки телефона и карты. В спайке S-05 OneDrive проверяется после появления каталога.

### WebDAV

- Общий коннектор для Nextcloud, ownCloud, Synology/QNAP и других NAS.
- Облако Mail.ru поддерживает WebDAV **только на платных тарифах** и с «паролем для внешнего приложения» —
  такие пользователи подключаются через этот коннектор.
- Пароль приложения храним только в защищённом хранилище ОС (Keychain / Keystore / системный keyring).
- Удаления в v1.0 нет: в протоколе WebDAV нет корзины, а удалять безвозвратно Pixroost не будет
  ([ADR 0011](../architecture/adr/0011-cleanup-safety-rule.md)).

### Общие папки облаков

В общих папках Яндекс Диска и Dropbox, в общих файлах и ярлыках OneDrive («Добавить в Мои файлы») один и тот же
файл виден в нескольких аккаунтах. Семейный сценарий: подключены аккаунты двух человек с общей папкой «Семья».
Удаление файла в одном аккаунте убирает его у всех участников папки.

Поэтому в v1.0:

- копия в общей папке не служит опорной копией для удаления в других источниках;
- удалить из общей папки Pixroost не предлагает, даже если есть проверенная копия в архиве;
- коннектор отмечает такие файлы: Dropbox — по `sharing_info` / `parent_shared_folder_id` и
  `has_explicit_shared_members` (файл, которым поделились с людьми напрямую), OneDrive — по `remoteItem` и
  общему доступу к файлу и папкам-предкам. Если признак получить нельзя или нужного поля нет в ответе, папка
  считается общей. Общий доступ не меняет ревизию файла, поэтому перед каждой партией признак читается заново;
- у Яндекс Диска документированного признака общей папки нет, используется поле `share`. Прототип S-05 проверил
  его на двух аккаунтах в 2026-10, владельце и участнике с правом только на чтение: `share` есть у корня общей
  папки (`is_root=true`) и у проверенных вложенной папки и файлов (`is_root=false`), в листинге папки и в прямом
  запросе, при `rights=rw` и `rights=r`; у необщей папки его нет; приглашение принимать не нужно. Читать признак
  можно только прямым запросом ресурса или листингом папки без `fields` (с `fields` без `share` поле пропадает) и
  не по плоскому списку `/resources/files`. Публикация файла по ссылке общим доступом не считается. Элемент в
  общей папке, если `share` есть у него или у любого предка, при любых `is_owned` и `rights`: такая копия не
  удаляется и опорой не служит. Остальные копии идут по обычному правилу. Если `share` пропал у корня известной
  (по `resource_id`) общей папки, а другие корни его отдают, доступ закрыт законно; если не отдаёт ни один,
  уборка в Яндекс Диске останавливается с предупреждением и вопросом пользователю
  ([подробно](../architecture/data-model.md#общие-папки));
- то же для папок синхронизации на ПК: удаление локальной копии клиент синхронизации повторит в облаке у всех.
  Признак берётся у копии того же облака по тому же пути; если это облако не подключено к Pixroost, копия
  считается общей. Папки, которые ПК точно определил как обычные, общими не бывают; если ПК не смог понять,
  папка ли это синхронизации, он спрашивает пользователя, а без ответа считает её папкой синхронизации
  ([как](../architecture/data-model.md#папки-синхронизации-на-пк)).

Свой домен хранения на каждую общую папку (одна папка — одно хранилище во всех аккаунтах) — возможное развитие
после v1.0 ([правило безопасности](../architecture/data-model.md#общие-папки)).

### Google Фото

- **С 31 марта 2025** Google закрыл сторонним приложениям чтение всей библиотеки Google Фото.
  Library API теперь работает только с файлами, которые приложение само загрузило.
- Остаётся **Picker API**: пользователь сам выбирает фото и альбомы в интерфейсе Google, приложение получает
  временный доступ к выбранному. Подходит для «забрать вот эти альбомы в архив». По спайку S-05:
  - выбор показывает только Google: на ПК — страница в браузере, на Android — приложение Google Фото.
    Встроить его в своё окно нельзя;
  - за одну сессию — до 2 000 фото; больше — несколькими заходами;
  - после «Готово» на Android Google Фото не возвращает в приложение: просим пользователя вернуться самому.
    Пока открыт Google Фото, Android может выгрузить Pixroost, поэтому сессия выбора хранится и продолжается
    после перезапуска;
  - файлы приходят в исходном формате (HEIF остаётся HEIF), но без геоданных в EXIF, то есть не байт в байт
    с оригиналом: точные дубли с другими источниками по хэшу не находятся, только по визуальному сходству;
  - вход: на Android — PKCE без секрета, своя схема приложения (в настройках Android-клиента включается
    «Custom URI scheme»). На ПК клиент Google типа Desktop без client secret код не обменивает, даже с PKCE.
    Google сам пишет, что секрет установленного приложения не считается секретом; в репозиторий он не попадает,
    в сборку подставляется из секретов CI;
  - access token живёт час и обновляется. В режиме Testing (до 100 тестовых пользователей) refresh token
    действует 7 дней.
- Копии из Picker и Takeout никогда не служат опорной копией для удаления в других источниках: доступ Picker
  временный, Takeout — разовая выгрузка, и проверить, что файл всё ещё лежит в Google Фото, нельзя
  ([правило безопасности](../architecture/data-model.md#правило-безопасности-удаления)).
- **Вся библиотека — через Google Takeout:** пользователь выгружает архив на [takeout.google.com](https://takeout.google.com/),
  Pixroost на ПК импортирует zip-файлы и восстанавливает даты съёмки из JSON-файлов-спутников.
  В приложении — пошаговая инструкция.
- Для публикации нужна верификация OAuth-приложения в Google Cloud: свой домен, домашняя страница,
  политика конфиденциальности.

### Google Диск

- Полный доступ на чтение (`drive.readonly`) — «ограниченная» область: нужен ежегодный платный
  аудит безопасности. **Не делаем.**
- Вместо этого — папка **Google Drive для компьютера** как источник на ПК.
- `drive.file` (доступ только к файлам, которые открыл пользователь) — кандидат на v1.x.

### Облако Mail.ru

- Официального публичного API нет, WebDAV — только на платных тарифах.
- **Бесплатные пользователи:** папка синхронизации приложения «Облако Mail» на ПК → источник-папка.
- Неофициальные API не используем: они ломаются и нарушают правила сервиса.

### Папки и диски на ПК

Универсальный адаптер ко **всему**, что умеет синхронизироваться с компьютером:

| Сервис | Откуда брать на ПК |
|---|---|
| iCloud Фото | Windows: «iCloud для Windows» синхронизирует фото в папку. macOS: v1.x — библиотека «Фото» |
| Google Диск | папка «Google Drive для компьютера» |
| Яндекс Диск, Облако Mail.ru, OneDrive, Dropbox | папки их desktop-клиентов (Яндекс Диск для ПК — только по подписке с июня 2026) |
| Внешние диски, флешки, старые архивы | любая папка |

Удаление из такой папки → корзина ОС → клиент облака удалит файл и в облаке.
Интерфейс предупреждает об этом явно. Поэтому папка синхронизации и само облако для правила безопасности —
одно хранилище: копия в одном не служит опорой для удаления в другом. Индексатор не заходит по символическим
ссылкам и junction, а одинаковость файлов сверяет по file ID, а не по пути.

Удаляем только на томах, где корзина ОС проверена. Корзина Windows молча удаляет навсегда файлы больше своего
предела и всё подряд на томе, где она отключена, а переполненная корзина сама выбрасывает старые файлы. Поэтому
ПК проверяет настройки корзины тома перед удалением, а срок хранения в журнале для корзины ОС не обещает
([корзина](../architecture/data-model.md#корзина)). Съёмные и сетевые тома Windows считаются томами без корзины,
а на Linux удаляем только туда, где на томе есть или создаётся корзина по спецификации freedesktop.org.

## Интерфейс коннектора

Все источники реализуют один контракт (подробнее — в [архитектуре](../architecture/overview.md)):

```kotlin
interface MediaSource {
    val kind: SourceKind
    val capabilities: Set<Capability>   // READ, THUMBNAILS, DELTA, QUOTA, HASH_MD5, HASH_SHA256, TRASH, RESTORE

    fun changes(cursor: SyncCursor?): Flow<ChangeBatch>      // инкрементальная синхронизация
    suspend fun quota(): Quota?
    suspend fun thumbnail(ref: RemoteRef, sizePx: Int): ByteArray
    suspend fun open(ref: RemoteRef): RawSource               // поток оригинала
    suspend fun trash(refs: List<RemoteRef>): TrashResult
    suspend fun restore(refs: List<TrashedRef>): RestoreResult // «Восстановить» из корзины, если есть RESTORE
}
```
